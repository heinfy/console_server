# 后端启动教程

本文适用于 `console_server`，涵盖首次本地启动、预发和生产启动、自定义环境及数据库初始化。
除明确写出绝对路径的示例外，所有命令都在后端项目根目录执行，即包含 `pyproject.toml` 和 `scripts/` 的目录。

## 1. 准备工具和依赖

准备以下工具：

| 工具 | 用途 |
| --- | --- |
| uv | 安装项目指定的 Python、创建虚拟环境及安装依赖 |
| Bash | 执行统一启动入口 `scripts/start.sh` |
| Docker 和 Docker Compose | 按项目现有配置启动本地 PostgreSQL；已有可用数据库时可以直接连接 |
| curl | 检查后端健康接口 |

macOS、Linux 可以直接使用以下 Bash 命令；Windows 建议在 WSL 中执行。

从包含前后端两个项目的 `console` 目录进入后端：

```bash
cd console_server
uv --version
docker compose version
uv sync --frozen
```

项目要求 Python 3.11 及以上，当前 `.python-version` 指定 `3.12.15`。
`uv sync --frozen` 按 `uv.lock` 安装依赖并准备项目 `.venv`，不会更新锁文件。
无需再单独执行 `uv venv`；启动脚本会自动寻找可用的 Python。

## 2. 首次启动本地开发环境

### 2.1 启动 PostgreSQL

```bash
docker compose up -d postgres
docker compose exec -T postgres pg_isready -U postgres
```

等待 `pg_isready` 输出 `accepting connections` 后继续。
项目现有 Compose 配置的容器名为 `console-db`，数据库用户为 `postgres`，
本地开发密码为 `123456`，映射端口为 `5432`。这些值用于下方本地配置示例。
Compose 当前只启动数据库，后端通过启动脚本单独运行。

### 2.2 创建并初始化新数据库

以下命令针对**新建的空数据库**：

```bash
docker compose exec -T postgres createdb -U postgres console_dev
docker compose exec -T postgres psql -U postgres -d console_dev -v ON_ERROR_STOP=1 < sql/init.sql
```

**`sql/init.sql` 包含 `DROP TABLE`、`DROP TYPE` 等重建语句，只用于首次初始化空库。**
如果提示数据库已存在，先确认它是否已完成初始化。开发库结构与当前代码不一致时，使用新的空库初始化；需要保留的数据应另行处理。

### 2.3 创建开发配置并生成密钥

首次创建配置文件，`cp -n` 会保留已存在的文件：

```bash
cp -n .env.example .env.dev
.venv/bin/python -c 'import secrets; print(secrets.token_urlsafe(64))'
```

将生成的随机字符串填写到 `.env.dev` 的 `SECRET_KEY`，并修改数据库连接。
使用上面的本地数据库时，配置如下：

```dotenv
DATABASE_URL=postgresql+asyncpg://postgres:123456@localhost:5432/console_dev
SECRET_KEY=
DEBUG=true
PORT=8000
COOKIE_SECURE=false
CORS_ALLOW_ORIGIN="http://localhost:5173;http://localhost:8000"
```

上面的 `SECRET_KEY` 留空是为了让你填写刚生成的密钥，填写后才能启动。
它用于签发和校验 JWT 登录令牌，当前应用要求所有环境都提供至少 32 字节、
不含首尾空白且不是示例占位值的密钥。开发、预发和生产分别生成并保存各自的密钥；
同一环境的多个服务实例使用相同密钥。更换密钥会使已有登录令牌失效。

已有 `.env` 的项目可以继续使用它；如果同时存在 `.env.dev`，开发启动只读取 `.env.dev`。

### 2.4 启动和访问后端

```bash
bash scripts/start.sh dev
```

开发启动默认开启热更新。保持该终端运行，在另一个终端检查服务：

```bash
curl --fail --silent --show-error http://localhost:8000/api/health
```

默认返回：

```json
{"detail":"ok"}
```

浏览器打开 `http://localhost:8000/docs` 可以查看并调试 API。
健康接口只确认应用能够响应请求；数据库初始化是否完成，还需要通过登录等实际访问数据库的接口验证。
在运行后端的终端按 `Ctrl+C` 停止服务。

## 3. 启动预发或生产环境

在构建或部署准备阶段安装运行依赖：

```bash
uv sync --frozen --no-dev
```

### 3.1 预发环境

```bash
cp -n .env.pre.example .env.pre
.venv/bin/python -c 'import secrets; print(secrets.token_urlsafe(64))'
```

编辑 `.env.pre`，填写预发数据库连接和刚生成的密钥。
模板中的 `user`、`password`、`pre-db` 和数据库名称都需要按实际部署替换。
首次部署按第 6 节准备好数据库结构，然后启动：

```bash
bash scripts/start.sh pre --dry-run
bash scripts/start.sh pre
```

部署平台通过环境变量选择预发环境时使用：

```bash
ENV=pre bash scripts/start.sh
```

### 3.2 生产环境

```bash
cp -n .env.prod.example .env.prod
.venv/bin/python -c 'import secrets; print(secrets.token_urlsafe(64))'
```

编辑 `.env.prod`，填写生产数据库连接和生产环境独立的密钥，准备数据库结构后启动：

```bash
bash scripts/start.sh prod --dry-run
bash scripts/start.sh prod
```

未传环境参数且系统没有设置 `ENV` 时，`bash scripts/start.sh` 默认选择 `prod`。
预发、生产和其他非开发环境默认关闭 DEBUG、热更新和 API 文档，默认使用一个进程。
模板中的 `COOKIE_SECURE=true` 用于 HTTPS 部署，本地开发通过 HTTP 访问时使用 `false`。

`--dry-run` 检查启动参数及必要变量是否已提供，并显示启动命令；它不启动应用、
不连接数据库，也不打印数据库地址或密钥。密钥长度等应用配置校验会在实际启动时执行。

脚本以前台方式运行。部署平台或 systemd 负责保活、重启及收集日志；停止信号会传递到 Uvicorn，执行应用关闭流程。
当前应用每个进程都会启动定时清理任务，因此先使用默认的 `WORKERS=1`。
增加进程或副本数量前需要处理定时任务的重复执行。

## 4. 测试、自定义环境和外部配置文件

### 4.1 增加自定义环境

例如增加 `uat` 环境：

```bash
cp -n .env.pre.example .env.uat
```

填写 `.env.uat` 中该环境的数据库连接和独立密钥，然后启动：

```bash
bash scripts/start.sh uat
```

同样，`bash scripts/start.sh test` 自动选择 `.env.test`。
环境名以英文字母开头，可以包含字母、数字、下划线和连字符，启动时统一转换为小写。

### 4.2 指定外部配置文件

如果部署系统把配置文件挂载到 `/etc/console/pre.env`：

```bash
bash scripts/start.sh pre --env-file /etc/console/pre.env
```

也可以通过环境变量设置：

```bash
ENV=pre ENV_FILE=/etc/console/pre.env bash scripts/start.sh
```

相对配置文件路径始终基于后端项目根目录；显式指定的文件不存在时会报错。
如果自动选择的 `.env.<环境名>` 不存在，也可以完全通过部署平台注入配置，
提供 `DATABASE_URL`、`SECRET_KEY` 等必要变量后启动。

## 5. 环境选择及常用配置

| 环境 | 入口 | 自动配置文件 | 默认 DEBUG / 热更新 |
| --- | --- | --- | --- |
| 开发 | `bash scripts/start.sh dev` | `.env.dev`，缺失时读取 `.env` | 开启 / 开启 |
| 预发 | `bash scripts/start.sh pre` | `.env.pre` | 关闭 / 关闭 |
| 生产 | `bash scripts/start.sh prod` | `.env.prod` | 关闭 / 关闭 |
| 测试 | `bash scripts/start.sh test` | `.env.test` | 关闭 / 关闭 |
| 自定义 | `bash scripts/start.sh uat` | `.env.uat` | 关闭 / 关闭 |

环境别名：`local`、`development` 对应 `dev`；`staging`、`preprod` 对应 `pre`；
`production` 对应 `prod`；`testing` 对应 `test`。别名读取规范名称的文件，
例如 `staging` 读取 `.env.pre`。应用的 `ENV` 由启动入口设置，配置文件无需填写。

配置优先级如下：

- 环境名称：命令行参数 > 系统 `ENV` > `prod`。
- 配置文件：`--env-file` > 系统 `ENV_FILE` > 自动选择的文件。
- 配置值：系统环境变量 > 所选配置文件 > 默认值。

每次启动只读取一个配置文件；预发、生产、测试和自定义环境不会自动读取开发用的 `.env`。
实际 `.env`、`.env.pre`、`.env.prod` 等文件被 Git 忽略，示例文件可以提交。

| 变量 | 作用及默认值 |
| --- | --- |
| `DATABASE_URL` | SQLAlchemy 异步数据库连接，格式为 `postgresql+asyncpg://用户:密码@主机:端口/数据库`；非开发环境必须显式提供 |
| `SECRET_KEY` | JWT 密钥，所有环境必须提供，至少 32 字节 |
| `PORT` / `HOST` | 默认 `8000` / `0.0.0.0` |
| `DEBUG` | 控制调试和 API 文档；开发默认 `true`，其他环境默认 `false` |
| `RELOAD` | 热更新，开发默认 `true`；非开发环境必须关闭 |
| `WORKERS` | 默认 `1`；开启热更新时必须为 `1` |
| `COOKIE_SECURE` | 开发默认 `false`，其他环境默认 `true` |
| `LOG_LEVEL` | Uvicorn 日志等级，默认 `info` |
| `GLOBAL_LOG_LEVEL` | 应用日志等级，默认 `INFO` |
| `FORWARDED_ALLOW_IPS` | 信任的反向代理 IP / 网段，默认 `127.0.0.1` |
| `ENV_FILE` | 显式选择配置文件 |
| `PYTHON_BIN` | 显式选择 Python；否则按已激活的虚拟环境、项目 `.venv`、系统 `python3` 的顺序寻找 |

例如临时覆盖端口，或关闭开发热更新：

```bash
PORT=8080 bash scripts/start.sh pre
RELOAD=false bash scripts/start.sh dev
```

端口改成 `8080` 后，健康检查地址也要改成 `http://localhost:8080/api/health`。
如果已激活其他项目的虚拟环境，可以用 `PYTHON_BIN` 显式指定当前项目的解释器。

## 6. 数据库初始化与结构变更

项目处于开发阶段，尚未部署预发和生产环境，当前只保留 `sql/init.sql` 作为新库初始化入口。
该文件包含权限目录、系统角色、删除外键约束、用户 UUID、登录会话及审计表，按第 2.2 节导入后即可启动后端。

应用启动时不会自动建表或修改表结构。开发期间结构变更后，可创建新的空库并导入当前初始化 SQL，
再更新环境文件中的 `DATABASE_URL`。

## 7. 常见问题

| 现象 | 处理方法 |
| --- | --- |
| `uv` 命令不存在 | 安装 uv 并确保所在目录加入 PATH，再运行 `uv --version` |
| 缺少 `uvicorn`、`dotenv` 或其他模块 | 在后端根目录执行 `uv sync --frozen`；部署用 `uv sync --frozen --no-dev`，确认所用 Python 属于已安装依赖的虚拟环境 |
| 提示必须提供 `DATABASE_URL` / `SECRET_KEY` | 检查选中的环境文件，填写值；开发环境也需要密钥 |
| `SECRET_KEY` 校验失败 | 使用第 2.3 节命令生成随机密钥，粘贴完整输出，检查首尾空白和环境变量是否覆盖了文件值 |
| `--dry-run` 成功，实际启动仍失败 | 启动预检没有导入应用；实际启动还会检查密钥格式及导入依赖，按报错修正 |
| `database does not exist` | 创建连接字符串中指定的数据库，确认配置与初始化命令中的库名一致 |
| `relation ... does not exist` | 检查连接的库名和初始化状态；新空库导入 `sql/init.sql`，开发库结构变更参阅第 6 节 |
| 数据库连接被拒绝 | 用 `pg_isready` 确认数据库就绪，检查地址、端口及密码；后端在独立容器中时，数据库地址填写容器网络中的数据库主机名 |
| 配置文件修改后没有生效 | 停止并重新启动后端，检查系统环境变量是否覆盖配置文件；开发热更新主要监控 `src/` |
| 预发 / 生产访问 `/docs` 返回 404 | 默认关闭 DEBUG；通过健康接口检查服务，开发调试使用 dev 环境 |
| 端口被占用 | 设置其他 `PORT`，例如 `PORT=8001 bash scripts/start.sh dev`，同步修改访问地址 |
| 热更新与多进程冲突 | 开发使用 `WORKERS=1`，或显式设置 `RELOAD=false`；非开发环境保持热更新关闭 |
| 本地 HTTP 登录后刷新 Cookie 无法发送 | 检查开发配置为 `COOKIE_SECURE=false`；HTTPS 部署使用 `true` |

查看启动入口帮助：

```bash
bash scripts/start.sh --help
```

## 8. 使用 Docker 部署

Dockerfile 已接入统一启动入口，并按 `uv.lock` 安装完整运行依赖。
预发和生产使用同一镜像，环境文件在运行时注入；镜像以普通用户运行，
自带 `/api/health` 存活探测。实际环境文件不会进入镜像构建上下文。

宿主机安装第 1 节的 Python 依赖后，用同一个入口部署后端：

```bash
bash scripts/start.sh pre --docker up -d --build
bash scripts/start.sh prod --docker up -d --build
bash scripts/start.sh pre --docker logs --tail=100 backend
```

入口自动加载 `.env.pre` / `.env.prod` 并选择 `docker-compose.deploy.yaml`；
不带 Compose 参数的 `--docker` 默认执行 `up -d`。启动器选项写在 `--docker` 前：

```bash
bash scripts/start.sh pre --env-file /etc/console/pre.env --docker up -d --no-build
bash scripts/start.sh prod --dry-run --docker
```

环境选择、别名和配置优先级与直接启动完全相同，脚本、应用导入和镜像的默认环境都为 `prod`。
`PORT` 同时设置应用监听和容器映射目标；宿主机端口默认等于 `PORT`，
只需改变宿主机端口时设置 `HOST_PORT=8001`。正式发布可先构建固定版本镜像，
再用 `CONSOLE_IMAGE=镜像标签` 和 `--no-build` 启动。
也可以通过 `docker run` / 部署平台注入 `ENV=pre`、`ENV=prod` 和对应数据库、密钥配置。
构建、配置、数据库初始化、端口映射和发布操作见 [Docker 部署教程](Docker部署教程.md)。
